# Правила роботи AI-агента — Telegram-боти

Адаптовано з `AI_RULES.md` проєкту croatian-survival-app (розділи 80–102) під Telegram-новинних ботів (молдовський і хорватський). **Це джерело правди** для поведінки AI в цьому репозиторії; `CLAUDE.md` посилається сюди.

Специфіка ботів, яка змінює правила порівняно з застосунком:
- Немає «білда» й окремого стенду: **кожен запуск `main.py` публікує в живий канал** і пише в робочу БД.
- Головні ризики — редакційні (що й як потрапляє в канал) і вартісні (хвилини GitHub Actions, токени Gemini), а не UX.
- «Контент» генерує Gemini в рантаймі, тому якість забезпечується промптами, фільтрами й моніторингом, а не рев'ю перед публікацією.

## 1. Порядок дій (Operating Rules)

AI на кожну задачу:

1. Читає `project_state.md` (стан, відкриті питання, задачі) і релевантні розділи `docs/`. **Звіряє його з GitHub** (§2.1 п. 5): PR, змерджені або закриті після останнього запису журналу → оновлює статуси й §1.
2. Оглядає наявний код (`main.py`, workflow, `setup_db.py`) і стан БД (лише `SELECT`).
3. Визначає залежності: Supabase-схема, секрети, cron-job.org, моделі Gemini, хорватський бот-близнюк.
4. Складає план і клас рішення (§3). Для `PROPOSE`/`HUMAN` — зупиняється й питає. Будь-яке нове чи змінене число (таймаут, повтор, поріг, ліміт, бюджет) — завжди `PROPOSE` з варіантами (§2.1 п. 2).
5. Реалізує. Якщо змінюється правило — спершу знаходить усі місця, де воно застосовується (§2.1 п. 7).
6. Перевіряє (§5 Release gate) — без публікації в основний канал.
7. Звіряє з критеріями приймання задачі.
8. Оновлює документацію: `project_state.md` (завжди), `docs/AUDIT.md`, `docs/ARCHITECTURE.md`, `db/schema.sql` — що зачеплено.
9. Звітує (§6).
10. Пропонує наступні задачі (§6).

## 2. Заборонено без погодження людини (AI Must Not)

- змінювати **редакційну політику**: аудиторію каналу, категорії «що публікуємо», стоп-теми, тон, мову, правила хештегів (тобто зміст промптів у `deduplicate_news` і `process_backlog`, а також редакторські списки: `unwanted_url_categories` і `unwanted_keywords` в `is_quality_article`, `UKRAINE_KEYWORDS`, `REJECTION_CATEGORIES`);
- додавати чи прибирати **RSS-джерела**;
- **запускати `main.py`** або workflow з робочими секретами (це публікація в канал) і надсилати повідомлення в канал чи адміну;
- видаляти або масово змінювати **робочі дані** в Supabase (`DELETE`, `UPDATE` без `WHERE` по конкретних рядках, `TRUNCATE`, `DROP`);
- **мовчки змінювати контракт БД** — таблиці, колонки, статуси, значення `status`;
- змінювати **моделі Gemini**, частоту запусків, `BATCH_SIZE`, паузи — усе, що впливає на вартість або обсяг публікацій; так само **таймаути, кількість повторів, пороги, ліміти й бюджети** (`FILTER_TIMEOUT_MS`, `MAX_BATCH_SIZE`, `RUN_TIME_BUDGET_SECONDS`, `MAX_AGE_SECONDS`, `SOURCE_ERROR_LIMIT`, `SOURCE_RETRY_HOURS`, поріг схожості 0.90 тощо) — і нові такі константи теж;
- вмикати платні функції або **збільшувати витрати** (бюджети GitHub, платний тариф Gemini, апгрейд Supabase);
- змінювати видимість репозиторію, секрети, токени, доступи, задачі cron-job.org;
- додавати нову інфраструктуру (сервіси, хостинг, черги) або нові залежності;
- пушити або мерджити в `main` без явного дозволу; писати напряму в локальну папку власника (усі зміни — гілка → PR → погодження → `git pull`, R-13).

### 2.1. Погодження, PR і документація (R-18, уроки аудиту 07.11.2026)
Аудит хорватського бота (PR #9–#30, його T-30) знайшов відхилення в роботі Claude. Власник погодив 7 правил для **обох ботів** (R-18):

1. **Промпти й редакторські списки — лише повністю погоджений текст.** Якщо в тексті є хоч одне слово, якого власник не бачив в остаточному вигляді (доповнення «за описом варіанта», стилістична правка, інший порядок слів), — зупинитись, показати остаточний текст повністю і чекати «так» **до** PR. Позначки «на перевірку в PR» заборонені. Промпти й списки — дослівно, без «покращень», перефразувань і скорочень; ніколи не видавати «повний новий файл» замість точкових змін.
2. **Числа — `PROPOSE`.** Таймаути, повтори, пороги, ліміти, бюджети (нові й змінені): спершу варіанти з обґрунтуванням і «так» власника, потім PR.
3. **Опис PR** — обов'язкові розділи:
   - «Що видалено або спрощено» (навіть «нічого»); якщо зміна прибирає функцію чи перевірку або помітно скорочує код — спершу спитати;
   - «Промпти змінено: так/ні» (якщо так — diff промпту);
   - «Редакторські списки змінено: так/ні» (списки з §2; якщо так — diff);
   - до кожної зміни промпту чи списку — **цитата «так» власника** з датою й часом;
   - **статистика diff** — вивід `git diff --stat origin/main...HEAD`, без словесних оцінок на кшталт «змінено лише 6 рядків».
4. **Без ланцюжків PR.** Кожен PR — окрема гілка від свіжого `origin/main` і не містить комітів іншого відкритого PR. Якщо зміна залежить від відкритого PR — чекати його мержу або об'єднати все в один PR (а зайвий закрити з поясненням).
5. **Документація після мержу.** На початку кожної сесії: `gh api "repos/<owner>/<repo>/pulls?state=closed&sort=updated&direction=desc&per_page=20"` → для кожного PR, змердженого чи закритого після останнього запису журналу, — запис у §7, статуси ✅ у §3/§4 і §1 «Остання версія коду». Час для «Останнє оновлення» і журналу — з годинника (`TZ=Europe/Warsaw date '+%d.%m.%Y, %H:%M'`) **безпосередньо перед комітом**, не оцінка й ніколи не в майбутньому.
6. **Відповіді власника — цитатою з часом.** У `project_state.md` відповідь записується дослівно в «лапках» з датою й часом (Europe/Warsaw). Якщо відповідь суперечить даним (скріншот, БД, код, GitHub) — спершу перевірити й показати розбіжність, лише потім будувати план.
7. **Повнота зміни правила.** Коли змінюється правило (стоп-слова, ліміт, перевірка, поріг, бюджет), знайти **всі** місця, де воно застосовується (`grep` за константою, списком, назвою функції: відбір, фільтр, переклад, перевірка перекладу, звіти, SQL), перелічити їх в описі PR і на кожне — тест.

_Уроки, з яких ці правила (хорватський бот): (1) речення в промпті фільтра дописав Claude, погоджено лише постфактум; (2) таймаути й денний бюджет змінено без окремого «так»; (3) зміни стоп-списків — лише в «Що видалено», «6 рядків» при +115; (4) PR з комітами інших PR; (5) стан і статуси в `project_state.md` відставали на тиждень, час «Останнє оновлення» — у майбутньому; (6) хибно записана відповідь про квоти Gemini; (7) правило змінено в одному місці коду, а в перевірці перекладу — ні._

## 3. Класи рішень

| Клас | Що | Приклади |
|---|---|---|
| **AUTO** — роби сам, потім звітуй | Внутрішня реалізація без зміни поведінки в каналі та вартості | рефакторинг, логування, обробка помилок, виправлення багів без зміни політики, тести, документація, `project_state.md` |
| **PROPOSE** — запропонуй план, чекай «так» | Архітектура, залежності, схема БД, моделі Gemini, розклад/частота, пороги фільтрів (0.90, 12 год, 40 кандидатів), таймаути, повтори, бюджети (§2.1 п. 2), зміни workflow, перенесення змін у хорватського бота | заміна моделі, нова колонка, `concurrency` у workflow, таймаут фільтра 90 с, стеля партії 12 |
| **HUMAN** — лише людина | Редакційна політика й аудиторія, джерела, бюджет і платні сервіси, видимість репозиторію, секрети | «публікувати спорт?», «додати Telegram-канал як джерело?» |

Сумнів між класами → обирай суворіший.

## 4. Definition of Done

Зміна готова, лише коли:

- ✓ вимоги задачі виконані;
- ✓ критерії приймання перевірені;
- ✓ код проходить `python -m py_compile` і лінтер (`ruff`, коли буде доданий — T-12);
- ✓ unit-тести на змінені чисті функції (`is_quality_article`, `extract_image_urls`, `prioritize_ukraine_news`, чистка гомогліфів, обрізка в `send_to_telegram`) — коли з'явиться `tests/` (T-12);
- ✓ перевірка без публікації в основний канал: тестовий запуск DRY_RUN (RUNBOOK §5.8) — обов'язково для змін у промптах, моделях і джерелах;
- ✓ обробка помилок: збій Gemini/Telegram/джерела не губить статті й не публікує неперевірене;
- ✓ аналітика: якщо змінюється воронка — `stats` і звіт адміну відображають зміну;
- ✓ вплив на вартість оцінений: хвилини Actions на запуск, токени Gemini;
- ✓ зміни БД — ідемпотентні й відображені в `db/schema.sql` та `setup_db.py`;
- ✓ тести на **кожне** місце, де застосовується змінене правило (§2.1 п. 7);
- ✓ в описі PR є «Що видалено або спрощено», «Промпти змінено: так/ні», «Редакторські списки змінено: так/ні», цитати «так» власника до змін промптів і списків і `git diff --stat` (§2.1 п. 3);
- ✓ PR не містить комітів іншого відкритого PR (§2.1 п. 4);
- ✓ документація і `project_state.md` оновлені; час — з годинника перед комітом (§2.1 п. 5);
- ✓ немає критичної регресії (бот публікує, звіт адміну приходить).

## 5. Release gate (перед мержем у `main`)

| # | Перевірка | Як | Зараз |
|---|---|---|---|
| 1 | Синтаксис | `python -m py_compile main.py setup_db.py` | ✅ можна |
| 2 | Лінт | `ruff check .` | ⏳ T-12 |
| 3 | Unit-тести | `pytest` | ⏳ T-12 |
| 4 | Тестовий запуск без публікації | Actions → Run workflow з галочкою «Тестовий запуск» на гілці PR (або `DRY_RUN=1 python main.py`); пости — в адмін-чат з позначкою ТЕСТ, БД не змінюється | ✅ з 30.10 (T-11) |
| 5 | Міграція БД | `db/schema.sql` ідемпотентний (повторний запуск без помилок) | ✅ вручну |

| 7 | Workflow | YAML валідний, секрети ті самі, є `timeout-minutes` | ✅ вручну |

| 9 | Вартість | оцінка хвилин Actions/місяць і токенів/добу не гірша за поточну, або погоджена | ✅ вручну |

## 6. Звіт після кожної завершеної задачі

AI повертає:

- **Зроблено** — що змінено (файли, коміти).
- **Перевірки** — які пункти gate пройдені, які ні.
- **Аналітика й вартість** — вплив на воронку, токени, хвилини Actions.
- **Відомі обмеження.**
- **Технічний борг** — нове → `D-NN` у `project_state.md`.
- **Редакційні ризики** — що може гірше потрапляти/не потрапляти в канал, ризик дублів, мова перекладу.
- **Ризики стабільності** — залежність від моделей, джерел, лімітів.
- **Рекомендовані 3 наступні задачі.**

AI може пропонувати пріоритети. **Остаточне рішення щодо пріоритетів — за власником (Product Owner).**
