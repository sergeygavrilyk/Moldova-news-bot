## 2. Знахідки та рекомендації

### ✅ A1. Бот не працював 22.10–30.10.2026 — ВИРІШЕНО 30.10 (репозиторій зроблено публічним, тестовий запуск успішний)
Після 22.10 19:04 UTC у базі немає жодного запуску. **Підтверджено сповіщенням GitHub (30.10): використано 100 % (2000 / 2000) хвилин Actions за білінговий цикл акаунта `sergeygavrilyk`; ліміт оновиться 01.11.2026.** Запуски блокуються, бо понад ліміт витрачати не дозволено (бюджет $0).
Розрахунок: ~11 запусків × ~5 хв білінгу × 22 дні ≈ 1200 хв лише цього бота; решту ліміту, найімовірніше, з'їв хорватський бот у тому ж акаунті.
Варіанти: (1) дочекатися 01.11 — тоді ліміт знову закінчиться приблизно 20–22.11, якщо нічого не змінити; (2) зробити репозиторії ботів публічними — для публічних репозиторіїв стандартні раннери GitHub Actions безкоштовні (спершу перевірити, що в історії git немає секретів); (3) дозволити платне перевищення через бюджет; (4) скоротити хвилини на запуск (A6).
Додатковий ризик: безкоштовний Supabase-проєкт ставиться на паузу після ~7 днів неактивності (на 30.10 проєкт ще активний).

### ✅ A2. `setup_db.py` створює застарілу схему — ВИРІШЕНО (PR #3)
У робочій базі є розширення `vector` і колонки `articles.embedding` та `articles.rejection_reason`, але `setup_db.py` їх не створює (їх додали вручну). При розгортанні з нуля кожен `INSERT` у `scrape_feeds` падатиме, і бот не збиратиме новини.
**Рішення:** фактична схема збережена в [`db/schema.sql`](../db/schema.sql); перенести `CREATE EXTENSION IF NOT EXISTS vector` та два `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` у `setup_db.py`.

### ✅ A3. Один збій вставки скасовує весь збір запуску — ВИРІШЕНО (PR #3: commit на кожну статтю)
`scrape_feeds` робить `commit()` лише наприкінці, а при помилці вектор-пошуку чи `INSERT` викликає `conn.rollback()` — це відкочує **всі** незбережені вставки та оновлення статусів джерел цього запуску. Статті не губляться назавжди (їх буде зібрано наступним запуском), але запуск фактично працює вхолосту.
**Рішення:** `conn.commit()` після кожної успішної вставки або `SAVEPOINT` навколо кожної статті.

### ✅ A4. Якщо фільтр Gemini впав — публікується без фільтра — ВИРІШЕНО (PR #3: публікація пропускається, статті лишаються в черзі)
`deduplicate_news` при помилці повертає всіх кандидатів як схвалених. Тоді в канал можуть піти дублі, спорт чи «світовий шум».
**Рішення:** при помилці фільтра пропускати публікацію в цьому запуску (статті лишаться `pending` до наступного).

### ✅ A5. Немає захисту від паралельних запусків — ВИРІШЕНО (PR #3: `concurrency` + `timeout-minutes: 20`)
Workflow не має `concurrency`. Ручний запуск під час планового (або дубль задачі в cron-job.org) може обробити той самий беклог двічі.
**Рішення:** у `news_bot_run.yml` додати
```yaml
concurrency:
  group: moldova-news-bot
  cancel-in-progress: false
```
та `timeout-minutes: 20` для job.

### 🟡 A6. Хвилини GitHub Actions витрачаються на очікування — неактуально після R-07 (публічний репозиторій); паузу 45 с залишено навмисно (ліміти Telegram, R-09)
На кожен запуск ~2,5 хв навмисних пауз (15 с + 3 × 45 с), а `setup_db.py` виконується щоразу. Це прямо впливає на A1.
**Варіанти:** скоротити паузу між постами до 10–20 с; запускати `setup_db.py` лише вручну; або зробити репозиторій публічним (секрети при цьому лишаються захищеними, а хвилини Actions для публічних репозиторіїв безкоштовні) — це рішення власника.

### 🟡 A7. Джерела в статусі `error` не відновлюються самі
Після 3 помилок поспіль джерело виключається назавжди. Рекомендація: раз на добу пробувати `error`-джерела знову або надсилати адміну алерт про перехід в `error`. Поки — ручне скидання ([RUNBOOK §5.3](RUNBOOK.md#53-повернути-джерело-після-помилок)).

### 🟡 A8. Відновлення `processing` рахується від `created_at`
Стаття, зібрана годину тому і щойно взята в роботу, формально «старша 30 хв» і може бути скинута в `pending` паралельним запуском. Без паралельних запусків (A5) це безпечно; надійніше — окрема колонка `status_changed_at`.

### ✅ A9. Звіт адміну показує «Ретрай: 0» завжди — ВИРІШЕНО 30.10 (PR #1)
`stats["gemini_retries"]` ніде не збільшується. Або рахувати повтори (callback `before_sleep` у `tenacity`), або прибрати з звіту.

### 🟡 A10. Причини відхилення не уніфіковані
Gemini пише одне й те саме різними словами («Вже є в історії», «Вже згадувалося в історії», «Історія»…), 352 відхилення без причини. Для аналітики варто обмежити `reason` переліком (`Literal[...]`/`Enum` у Pydantic-схемі `RejectedItem`).

### ✅ A11. Назви моделей зашиті в код — ВИРІШЕНО 30.10 (PR #1: GitHub Variables + каскад під квоти free tier)
Коли Google зніме `gemini-3.6-flash` / `gemini-3.5-flash-lite` з обігу, впадуть обидві ланки фолбеку. Рекомендація: винести в змінні середовища (`GEMINI_FILTER_MODELS`, `GEMINI_TRANSLATE_MODELS`) із поточними значеннями за замовчуванням.

### 🟡 A12. Залежності без верхніх меж
`requirements.txt` містить лише `>=`; `google-genai` швидко змінює API. `pydantic` використовується напряму, але не вказаний (приходить транзитивно). Рекомендація: зафіксувати версії, що зараз працюють (`pip freeze`), і додати `pydantic`.

### 🟡 A13. Вектори та індекси
3072-вимірні вектори не можна проіндексувати HNSW для типу `vector` (ліміт 2000). При 3 тис. рядків повний перебір прийнятний; якщо база росте — `output_dimensionality=768` в `embed_content` або `halfvec`. Індекси на `articles(status, created_at)` поки не потрібні (запити йдуть мілісекунди).
